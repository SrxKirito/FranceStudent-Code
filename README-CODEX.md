# Copie de FranceStudent IDE avec le moteur Codex

Double-cliquer sur **Lancer-IDE-Codex.cmd**. Cette copie utilise Codex pour l’agent Code et le compte FranceStudent pour les modèles. Le chat classique et l’agent Motion conservent leur moteur existant.

L’agent Code Codex ne reçoit pas automatiquement `/index` ni un résumé IA de tout le projet. Son dossier de travail est transmis à Codex ; il liste, cherche et lit les fichiers au besoin. L’ouverture du projet prépare encore un index local et les sauvegardes, sans appel au modèle. La commande explicite `/index` du moteur historique peut demander un résumé IA payant. Les fichiers effectivement lus, les catalogues d’outils et l’historique utile consomment toujours du contexte : aucun pourcentage universel d’économie n’est garanti.

Roblox Studio et Blender utilisent leurs logos et le même composant de carte que GitHub. Après **Vérifier la connexion** avec une vraie session, ils passent dans **Plugins → Installés** et obtiennent un raccourci sous **Installés** à gauche. Cette validation est conservée dans le profil local et liée à la configuration MCP : une suppression, une désactivation ou un changement de commande la rend caduque. « Installé » ne signifie pas que l’application est actuellement connectée.

Le transport distingue explicitement `commentary` et `final_answer`. Un commentaire produit `end_turn:false` pour que Codex poursuive réellement ; deux commentaires successifs sans outil sont la limite avant correction. Les arguments sont validés avant émission, les variantes JSON complètes courantes sont normalisées et une seule correction de format est autorisée. Un appel tronqué n’est jamais complété puis exécuté. Une panne réseau arrête la tâche avec un message lisible ; aucune mutation déjà exécutée n’est rejouée automatiquement. La qualité des décisions reste dépendante du modèle.

Contrôles du 2 novembre : build et cohérence du renderer, syntaxe des modules modifiés, aperçu isolé Motion → Code avec notices de session et classement des plugins. Une simulation locale dans le vrai app-server a enchaîné commentaire, correction d’arguments, commande PowerShell réussie et réponse finale (aucun appel au fournisseur). La persistance et l’invalidation de l’installation ont été vérifiées avec un MCP simulé. Pas de suite automatisée ni nouvelle validation de connexion dans Studio/Blender réels.

En développement, la copie utilise le dossier voisin `francestudent-ide-codex-data`. Dans un paquet installé, elle utilise le profil utilisateur standard de l’application. Ne partage pas ces données : elles contiennent la session chiffrée, les conversations et les sauvegardes. Les paquets préparés embarquent Codex et cloudflared ; le développement utilise Node et Codex disponibles localement. Il faut toujours se connecter à FranceStudent pour utiliser ses modèles.

Les conversations locales de l’agent portent un identifiant `codex:` et apparaissent dans l’historique habituel. Les rouvrir permet de poursuivre après fermeture. Le journal visible est distinct des instructions internes et du contexte du modèle. Les tâches interrompues ne se réexécutent pas automatiquement.

Le bouton **+** à gauche de **Projets** crée un dossier de projet ou ouvre un dossier existant. Les projets enregistrés restent visibles même sans discussion. **Supprimer le projet de la liste** masque son entrée et ferme le projet s’il est ouvert ; fichiers, conversations et sauvegardes restent conservés. Rouvrir le dossier le rétablit. Les fichiers non enregistrés font l’objet d’une confirmation avant fermeture. Le registre utilise `hiddenAt`, sans réinitialisation du profil ni effacement des journaux.

## Réduction des requêtes et du contexte

Le pont emploie un protocole de transport plus court, sans les répétitions systématiques d’exemples, de demandes et de résultats. Les catalogues d’extensions identiques sont transmis une seule fois dans un même contexte. Les schémas d’outils, leurs contraintes et les instructions de projet sont conservés.

Quand le lecteur `read_context` est disponible, les sorties textuelles longues ou répétées sont abrégées avec une référence permettant de les relire sans réexécuter la commande. Les images ne sont pas abrégées et les anciennes conversations sans lecteur conservent leurs résultats complets. Le cache local est limité à 32 Mo et deux heures sans lecture, séparé par conversation. Ce sont des snapshots passés, pas des preuves de l’état actuel du disque.

Les skills installés sont proposés par domaines indicatifs (code, design, finance, documents, recherche) selon la demande. Les skills explicitement nommés restent proposés ; en mode manuel, ils doivent être nommés. Les instructions complètes sont chargées à la demande avec `use_skill`.

Les compteurs de session reçoivent désormais les appels et usages du processus Codex. Aucun appel IA de résumé n’est ajouté par cette optimisation. Le gain de quota dépend du modèle, des images et de la facturation FranceStudent : aucun pourcentage de baisse réelle n’est garanti. Une démonstration locale fortement répétitive est passée de 864 530 à 9 701 caractères de contexte, avec relecture exacte du contenu ; cela ne mesure pas une économie de facturation. Un parcours réel isolé de lecture de fichier a abouti en deux appels (85 830 caractères transmis au total). Un premier essai en lecture seule avait été interrompu par le contrôle de commande Windows ; il n’a confirmé aucune lecture. Ces deux essais de validation ont utilisé trois appels au total. Les contrôles de registre et d’aperçu n’utilisent pas le modèle ; aucune suite automatisée n’a été lancée.

Les cartes **Roblox Studio** et **Blender** sont disponibles dans **Plugins**. Le [guide des connexions](plugins/README.md) décrit le serveur officiel de Studio, l’extension Blender fournie et les prérequis restant à installer ou choisir sur ce PC.

Les sauvegardes avant demande utilisent `src/project/file-versions.js`, ses exclusions et ses limites. Si une sauvegarde requise échoue, la tâche ne démarre pas. Le panneau Sauvegardes permet de consulter les différences et restaurer avec vérification des changements concurrents et version de sécurité. Les sauvegardes de fichiers ne restaurent pas les actions externes d’une commande.

Le résumé repliable des actions présente les fichiers réellement créés ou modifiés et les commandes terminées. Les noms sont cliquables et les résultats restent consultables. Les nouveaux journaux conservent ces métadonnées à la relecture. Les onglets non modifiés sont rafraîchis après les actions ; les modifications manuelles non enregistrées sont préservées du rechargement.

Les réglages d’accès de l’IDE pilotent les confirmations des commandes et des fichiers, et les questions interactives restent des questions utilisateur. Codex applique ses propres permissions : les règles du moteur historique ne sont pas déclarées équivalentes. Le web utilise le MCP local du prototype. Les groupes d’outils choisis filtrent les outils correspondants du pont. Motion garde son moteur et ne démarre pas le runtime Codex Code.

## Pièces jointes, connexions et sous-agents

Les images jointes sont transmises au modèle par le service FranceStudent, avec les contrôles de taille et de décodage habituels. Le texte de transport remplace les données binaires par des repères numérotés ; les pixels sont réellement joints à la requête. La vision reste dépendante du modèle choisi. Les images renvoyées par un MCP, une capture ou une page PDF suivent ce même chemin. Le journal visible omet les données binaires et les catalogues internes ; le contexte Codex local peut conserver les images.

PDF, Word, tableurs, présentations, textes et archives utilisent les convertisseurs existants de l’IDE. Les archives conservent la sélection des fichiers. Les gros documents et les PDF restent indexés dans le processus de l’IDE et se lisent par `read_attachment`, avec pagination et recherche. Ces index expirent après deux heures sans lecture ou à la fermeture de l’application : ajouter de nouveau la pièce jointe si nécessaire. Limites actuelles : 20 pièces jointes par demande, 25 Mo par fichier avant conversion, 20 images dans le contexte et limite totale de la requête locale de 128 Mo. Le son et la vidéo donnent leurs métadonnées, sans transcription ni visionnage.

Le pont expose les MCP configurés, GitHub, les skills et le navigateur de capture. Les appels passent par les validateurs, les groupes sélectionnés et les confirmations existantes. Le mode lecture seule bloque les outils à effets externes. Un MCP ayant renvoyé une exécution incertaine n’est pas relancé avec les mêmes arguments pendant la tâche. Les outils déjà démarrés peuvent avoir produit des effets avant une interruption.

L’IDE continue de recevoir les événements d’arrêt et d’expiration pendant une confirmation. Une demande expirée est retirée de la file. Pour un appel MCP, une confirmation arrivée après l’annulation ne lance pas l’action. Un résultat incertain est signalé comme tel et doit être vérifié dans l’application concernée avant toute nouvelle tentative.

Les commandes et les modifications de fichiers utilisent les outils natifs de Codex. Les connexions externes dépendent des serveurs MCP configurés dans l’IDE ; les outils historiques de fichiers et diagnostics ne sont pas exposés dans ce moteur.

Les nouvelles conversations exposent directement les connecteurs, les skills, le lecteur de contexte et les outils natifs Codex. Les anciennes conversations peuvent découvrir les connecteurs via MCP ; la compression n’est activée que si leur lecteur est présent dans le catalogue. Les groupes et modes filtrent les outils pour chaque demande.

Si le modèle déclare les outils locaux indisponibles avant toute observation, le pont tente une lecture du projet ou découvre d’abord les outils de lecture via `tool_search`. Si la correction du format ou la reprise échoue, le pont peut choisir une seule fois un autre modèle actif du catalogue FranceStudent pour poursuivre la tâche. Il lui transmet le contexte de la tâche et affiche son nom pendant la reprise. Les autorisations, le mode lecture seule et le modèle sélectionné pour la prochaine demande restent en vigueur. La reprise ne contourne pas un refus d’autorisation et peut consommer des requêtes supplémentaires.

Au premier lancement, le lanceur importe les configurations MCP et skills utilisateur de l’ancien profil de FranceStudent, et la connexion GitHub uniquement si elle est déjà chiffrée. Il conserve toute configuration déjà présente dans la copie. Configurer ensuite les MCP et GitHub dans les réglages de cette copie ; le gestionnaire de l’IDE prend actuellement en charge les MCP stdio. Une application tierce (Blender, Studio, navigateur) doit être installée et disponible pour que son outil fonctionne. Cette passerelle n’importe pas les connexions, jetons, plugins privés ni outils hébergés de Codex desktop/ChatGPT. Un service comme Gmail ou Notion nécessite son propre connecteur MCP et son authentification dans l’IDE.

La délégation utilise les vrais sous-agents Codex : jusqu’à trois enfants, un niveau de profondeur, même modèle et fournisseur FranceStudent que le parent, restrictions héritées. Le groupe « Analyse déléguée » doit être sélectionné ; le mode Éco la désactive. Les requêtes au modèle sont sérialisées par la passerelle afin de ne pas mélanger l’état du fournisseur. Chaque action porte un identifiant de thread et d’appel pour associer correctement son résultat, même s’il arrive avant celui d’un autre agent. L’arrêt est transmis aux agents en cours ; la fin du parent interrompt les enfants encore actifs.

Cette copie reste expérimentale : fournisseurs personnalisés et mode éphémère sont explicitement refusés. Le chat classique reste disponible. Les hooks historiques autour des commandes natives Codex, `/undo` et tous les cas de changement de modèle demandent encore une intégration ou une validation dédiée. Utiliser les Sauvegardes pour revenir sur les modifications Codex. L’adaptateur utilise le binaire Codex installé ; le code Rust de Codex n’a pas été modifié ni recompilé.

Vérifications réalisées : compilation du renderer ; création puis relecture réelles d’un fichier via le backend de la copie ; enregistrement du journal visible ; reprise de la même conversation dans un nouveau processus avec restitution d’un mot de contrôle ; restauration d’un fichier avec version de sécurité. Dans le prototype : reprise après redémarrage et refus d’un aperçu de restauration périmé. Le résumé d’actions a été contrôlé visuellement avec les fonctions du renderer et le journal réel, et la copie Electron a été lancée. Les parcours manuels du 1er novembre 2026 ont ensuite confirmé avec le modèle FranceStudent sélectionné : lecture des pixels d’une image et du fichier sélectionné dans un ZIP, lecture de documents Word et Excel, lecture et rendu visuel d’une page PDF, appel MCP de démonstration après confirmation utilisateur, interprétation d’une image renvoyée par ce MCP et lecture d’un fichier par un vrai sous-agent (thread distinct), attente de son résultat puis fermeture. Le résumé des sous-agents et l’association hors ordre de ses résultats ont été vérifiés avec ce journal réel, sans résultat manquant. Les services et applications personnels n’ont pas été appelés pour ces contrôles.

Références du protocole : [Codex app-server](https://learn.chatgpt.com/docs/app-server), [sous-agents](https://learn.chatgpt.com/docs/agent-configuration/subagents). Le code du binaire installé reste la référence pour les options expérimentales.

Aucune suite automatisée complète n’a été lancée, conformément aux consignes du dépôt. Les autres parcours, tous les modèles et macOS ne sont pas validés. Les crédits FranceStudent et tiers sont conservés ; licence et notice Codex accompagnent le runtime dans `desktop/codex-runtime/`. `build.appId`, nom du paquet et version de publication restent inchangés. Aucune release, aucun commit ni push n’a été effectué.
